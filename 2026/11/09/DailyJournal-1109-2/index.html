MySQL延迟关联的原理讲解与实例

2026-11-09 09:51:29 ｜

延迟关联的本质是把「回表」这一动作推迟到最后：内层子查询只在索引上完成扫描、排序和分页，只产出 10 个主键；外层再拿这 10 个主键做等值查询取整行，于是回表从 100 万次降到 10 次。

问题出在哪里：limit 1000000, 10 并没有“只取 10 行”

MySQL 执行带大 offset 的 limit 时，会先按顺序生成前 1000010 条记录，再把前 1000000 条丢掉。关键在于“生成”这个动作：如果你写的是 select *，那么每生成一行，InnoDB 都要完成一次回表。

InnoDB 的二级索引叶子节点里只存「索引列 + 主键」，不存其他列。所以 where status=1 order by created_at 这类查询能靠索引定位到行，但要拿到 amount、remark 这些字段，必须拿着主键再回聚簇索引查一次整行，这就是回表。100 万次回表意味着访问 100 万个聚簇索引页，每页 16KB，而你真正需要的只有最后 10 行的几十个字节。如果排序走的是 created_at 这种非主键列，主键在二级索引里是乱序的，回表就是彻底的随机 IO，代价再翻几倍。

延迟关联怎么绕开它

改成你贴的写法后，执行被切成两段：

内层 select id 是一个覆盖索引查询。因为 id 就是主键，而二级索引天生带主键，所以 (status) 这个索引就能满足内层全部需求，Extra 里会出现 Using index，全过程不回表。它要扫描 1000010 个索引项，但每个索引项只有几十字节，纯顺序读，量级大概是几十 MB；而优化前是 100 万次页访问，量级上千 MB 且大概率随机。

拿到这 10 个 id 之后，外层 on t.id = x.id 是主键等值查找，执行计划里是 eq_ref，每次都是一次 B+ 树下降，成本可以忽略。这就是“延迟”两个字的含义：把最贵的整行读取，延后到结果集已经缩小到 10 行的时候再做。

三个必须满足的前提

这套优化不是无条件生效的，缺一条就会被打回原形。

第一，内层必须是覆盖索引扫描。也就是 where 条件列和 order by 列要落在同一个索引里，并且 select 列表里只能出现索引里已有的列（这里就是 id）。如果写成 select *，子查询本身就要回表，优化完全消失，MySQL 不会替你改写。

第二，排序要走索引顺序，不能 filesort。以 where status = 1 order by id 为例，InnoDB 二级索引 (status) 的物理顺序其实是 (status, id)，所以 status 取等值后 id 天然有序，可以直接顺着索引读，不需要额外排序。但如果你写成 order by created_at 而索引是 (status)，就会触发 filesort，内层虽然不回表，却要把所有满足条件的 id 读进排序缓冲区甚至临时文件再排，内存和 CPU 开销可能反过来超过回表。

第三，where 条件要能被索引有效过滤。如果 status 上没有索引，或者条件选择性极差（比如 99% 的行都满足），内层扫描量依然是全表级别，延迟关联只能省掉回表，省不掉扫描。

用 EXPLAIN 验证时，两段应该长这样：

层级 type rows Extra
内层 derived index 1000010 Using where; Using index
外层 t eq_ref 10 NULL

只要内层的 Extra 里没有 Using index，说明覆盖索引没成立，需要补索引或调整 select 列表。

它的天花板在哪里

延迟关联降低的是回表的次数，但没有降低扫描的深度。内层依然要顺着索引走过 offset + limit 条记录，复杂度还是 O(offset)。offset 到一千万时，即使全程覆盖索引，一千万次索引项读取和 B+ 树页跳转也不会便宜，只是比回表便宜一个数量级而已。

所以真正深的分页，更彻底的解法是游标分页（keyset pagination）：把“第几页”换成“上一页最后一行的位置”，where status = 1 and id > :last_id order by id limit 10。这样 B+ 树直接 seek 到起点，复杂度是 O(limit)，与页码无关，代价恒定。代价是不能随机跳页，只适合“下一页 / 滚动加载”这类交互。

实践中常见的取舍是：后台管理系统需要跳到第 5000 页，用延迟关联；面向用户的列表只做“加载更多”，用游标分页；两者都撑不住时，才考虑把这份查询搬到搜索引擎或做冷热分离。延迟关联的定位很清楚：它是一个低成本、不改业务语义、只改 SQL 形态的中间档优化，尤其适合你已经有合适索引、只是不想为了分页去建一个超宽覆盖索引的场景。
